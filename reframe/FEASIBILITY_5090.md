# REFRAME：RTX 5090 首轮可行性验证

2026-09-13；被测代码：`cef78a6678590f2d4885c5c346b240f899d285b6`。

**结论：当前全层 pair 方案没有通过加速验证，不建议直接投入全量 benchmark。**
真实 LLaDA-8B 上，REFRAME pair 在两题重复计时和另外四题开发检查中，
平均都耗时约为原版 Fast-dLLM v1 DualCache 的 3.7 倍。
这否定了当前配置和实现的实用加速价值；还不能证明所有参考坐标缓存方法都不可行。

## 已完成的验证

- 使用服务器物理 GPU 3，单张 RTX 5090 32 GB，所有 GPU 作业由 tmux 运行。
- 模型、数据全部读取现有离线缓存；没有训练、下载新权重或改动 v1/v2。
- 修复真实 checkpoint 配置加载：显式使用本地 `LLaDAConfig`，避免远端旧配置
  缺少 `train_max_sequence_length`；修复 lm-eval 0.4.8 的 prompt 日志回放。
- 服务器测试 **43 passed**，含 FlashAttention；真实 8B 的 oracle、audit、计时均运行成功。
- 所有验证作业成功退出；结束时 GPU 3 显存占用 0 MiB、利用率 0%。

环境为 PyTorch 2.7.1+cu128、CUDA runtime 12.8、FlashAttention 2.8.3.post1、
Transformers 4.49.0、Accelerate 0.34.2、lm-eval 0.4.8、datasets 5.0.0。

## 协议与范围

固定 LLaDA-8B-Instruct、BF16、FlashAttention、batch 1、生成长度 256、块长 32、
greedy decoding、置信阈值 0.9。REFRAME 使用每侧 16 个 pilots（通常 12 个拟合、
4 个验证），每两块完整刷新一次，残差门槛 0.25，scale 范围 [0.25, 4]。
没有根据本轮结果调整参数。

主计时复用已有 GSM8K smoke 的两道测试题及其完整 5-shot prompt。
每题每方法预热一次、测量三次，轮换执行顺序，每次生成重新初始化缓存。
六条记录仍然只有**两道独立题目**。同一题同一方法三次输出 token 完全一致。

补充检查使用 GSM8K **训练集**索引 1000、1100、1200、1300，固定训练集 0–4
作为 demonstrations。每题每方法预热一次、测量一次；这些是开发样本，不能报告为
GSM8K 测试集准确率。没有在这四题上拟合或调整算法参数。

计时包含一次生成中的初始完整计算、pilots、拟合、缓存写回和所有回退；
排除加载权重、分词、答案评分。oracle、audit 和插入 CUDA events 的诊断
单独执行，不混入主计时。

## 真实耗时

两道 smoke 题，每题三次，先对每题求均值，再对两题求均值：

| 方法 | 平均生成耗时 | 相对原版速度 | 平均完整 forward | 平均回退 |
| --- | ---: | ---: | ---: | ---: |
| 原版 v1 DualCache | 4.271 秒 | 1.000× | 8.0 | 0.0 |
| REFRAME stale | 8.190 秒 | 0.522× | 4.0 | 0.0 |
| REFRAME shift | 13.890 秒 | 0.308× | 44.5 | 43.0 |
| REFRAME pair | 15.833 秒 | 0.270× | 59.0 | 58.0 |

这里 stale 是 REFRAME 执行器中的“不校正、降低刷新频率”控制组。
它把完整 forward 从 8 次降到 4 次，但总耗时仍接近翻倍，说明减少刷新次数
没有转化为当前执行器的时间收益。

另外四道开发题：

| 方法 | 平均生成耗时 | 相对原版速度 | 平均完整 forward | 平均回退 |
| --- | ---: | ---: | ---: | ---: |
| 原版 v1 DualCache | 3.077 秒 | 1.000× | 8.0 | 0.0 |
| REFRAME stale | 6.319 秒 | 0.487× | 4.0 | 0.0 |
| REFRAME pair | 11.455 秒 | 0.269× | 57.5 | 56.5 |

pair 在四道开发题上逐题都更慢。两组数据的 pair 部分计算尝试分别约有
71.2% 和 80.7% 触发完整回退。触发条件主要是变换 scale 超出允许范围，
其次是验证 pilots 的残差过大。

日志的 REFRAME NFE = 完整 forward + 部分 forward **尝试**，包含被中途取消的尝试，
不等同于成功解码决策数。主计时的平均 NFE：原版 98.5、stale 95.5、shift 126.5、pair 140.5。
峰值 PyTorch allocated memory 分别约为 18.45、16.61、16.95、16.95 GiB；
这些值不包含 allocator 保留空间及全部非 PyTorch 显存，不能当作 nvidia-smi 总占用。

## 校正本身是否有效

oracle 在原版 DualCache 的真实轨迹上，使用当前完整 KV 拟合少量旧/新 pilots，
检查未参与拟合和验证的 token。其它位置使用当前真实 KV，分别隔离 prefix/suffix
的误差。它给出的条件比线上稀疏执行更理想，因此**不能用于证明线上速度**。

检查层 0、16、31，参考年龄 1/2/4 块，pilots 数 8/16/32，共 2160 条相关诊断记录。
这些记录来自两道题，不能当成 2160 个独立样本。以下为年龄 1 块、16 pilots，
attention 输出相对 Frobenius 误差的均值：

| 缓存区域 | stale | shift | scale | pair | pair 通过 scale 检查 |
| --- | ---: | ---: | ---: | ---: | ---: |
| prefix，42 个观测 | 0.1172 | 0.1324 | 0.1297 | 0.1457 | 33/42 |
| suffix，36 个观测 | 0.0487 | 0.0420 | 0.0472 | 0.0407 | 12/36 |

prefix 上 pair 的平均误差反而增大；该现象在 8/16/32 pilots 下都出现。
suffix 上有误差下降，但很多变换不满足当前执行器的 scale 限制。
观测中包含本来就几乎不变的层/状态，不能把这些均值解释为所有层都获得相同效果。

所有 oracle 记录中，“读取侧变换”与“显式物化变换后 KV”的最大相对差异为
0.00377。结合代数测试，这支持两种执行方式基本一致；无法据此证明 KV 近似准确。
**当前瓶颈不只是内核速度，拟合假设在 prefix 上也没有得到支持。**

## 质量检查的边界

同状态 audit 每四次决策检查一次，共 42 个检查点：

- 平均 logits 相对误差 0.01691，最大 0.13302。
- 每个检查点 masked-token top-1 一致率的均值为 98.64%。
- 3/42 次提交位置集合不同；日志记录的提交 token 一致性检查没有发现分歧。

这些检查包含完整刷新/回退后的状态，高一致率部分来自频繁完整计算，
不能解释成“近似路径无损”。提交位置变化本身就可能改变后续去噪轨迹。

先前 smoke 的两个最终数字都正确；原版 DualCache 严格匹配低分来自没有采用
`####` 格式。四题开发检查用 lm-eval 数字提取规则时三个方法均为 3/4，
也不足以建立质量结论。逐条查看显示，train_1200 的原版/stale 已算出 200 分钟，
但句末的“4 weeks”使最后数字提取成 4；pair 算出 200 分钟后又转成 3.33 小时。
因此这一个计分失败也不能直接归因于数学推理失败。

## 原版刷新到底占多少时间

额外使用 CUDA events 分别记录原版完整/部分 forward。每题先预热；插入 events 后
检查 NFE 与所有输出 token 与未插桩运行完全相同。此表是诊断，不替代主计时：

| 题目 | 8 次完整 forward 总耗时 | 占该次生成墙钟时间 | 免费省去交替 4 次刷新时的估算速度 |
| --- | ---: | ---: | ---: |
| smoke 0 | 1.150 秒 | 22.61% | 1.127× |
| smoke 1 | 1.151 秒 | 32.87% | 1.197× |

最后一列保持原版其它计算与输出轨迹不变，将 8 次完整 forward 中第 2/4/6/8 次
耗时直接扣除，并假设替代过程完全免费。真实 REFRAME 还需要 pilots、拟合、写回，
而且 NFE 会变化。这是**当前刷新策略、当前两题下的乐观成本估算**，不是所有长度、
所有 REFRAME 变体的理论上界。

它说明：当前每两块刷新一次的策略，即便工程开销理想化，也不支持直接预期
1.5–2 倍收益。要追求更大收益，需要证明还能削减其它成本或改变刷新策略。

## 后续决策

暂停当前全层、prefix/suffix 共用复杂 pair 变换的全量评测和大规模内核优化。
如果继续研究，先重新定义有潜力的目标：是否存在特定层/区域的可预测变化，
以及更便宜的读取校正能否覆盖足够大的实际耗时。suffix 的局部改善只是一条线索。

从代码可以看到逐层安全检查导致同步、cache gather 和分组 attention 等额外工作。
这些是合理的开销来源，但本轮没有逐 kernel 分摊 REFRAME 耗时，不能声称已量化
每一项贡献。也不应只放宽回退门槛来制造速度：那需要重新验证未刷新路径的误差。
